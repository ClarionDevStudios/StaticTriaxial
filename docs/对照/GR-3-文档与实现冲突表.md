# GR-3：协议文档 vs 实现 冲突与裁决表

建立于 2026-10-10（M2）。三个来源：

- **文档**：《综合性能_沥青万能机（GR-3）通讯协议 V1.0》——工作区 `E:\AiStudy\CodeX\docs\gr3-protocol.txt`
- **现役 Delphi**：`E:\Work\沥青力学试验软件\沥青综合性能试验软件\Common\UdpClientEx.pas` 等
- **.NET 参考实现**：`E:\AiStudy\CodeX\src\IndustrialCommsConsole\Protocols\Gr3\`（已联机验证过）

裁决原则（沿用 GLT-50 那次）：**冲突处以能跑的实现为准**；只被间接证明的，标「待抓帧确认」。

| # | 位置 | 文档怎么说 | 实现怎么做 | 裁决 |
| --- | --- | --- | --- | --- |
| 1 | A1H 应答的数据字节 | 格式行与举例写作 `Order(1)`，字段表写作 `STATUS`（0=校验失败 / 1=成功 / 2=无法执行） | 现役 `ProtocolTypes.pas` 有 `A1_STATUS_CHECKSUM_FAIL / SUCCESS / CANNOT_EXECUTE`；ICC 按 Status 解析 | **按 STATUS**。`Order` 是从别处复制来的笔误（A1 没有回显请求序号的需求） |
| 2 | A4H 的格式行 | 写作 `… Length(1) Order(1) Data(N) CRC(1)` | 同一张表的字段区写「命令类型 = 0xA4」 | **第 5 字节是命令类型**，`Order` 同样是笔误 |
| 3 | A4H 数据域长度 | 未给整体长度；字段表为 ID(24 ASCII) + 设备类型(UInt16) | ICC 按 26 字节解析 | **数据域 26 字节、指令包帧长度 28**（1 + 26 + 1） |
| 4 | 联机后上行 | C0 节：「通过验证后**首先返回 A0 和 A4**，然后进入联机模式」 | ICC 实测流程是联机后用 **CAH order=2 主动读** A4 | **两条路都保留**；ANX 在 M2 按「主动读」实现。是否会自动推 A0/A4 —— **待抓帧确认** |
| 5 | 实时数据速率 | C0 节：「以太网下以设定的 **120Hz** 帧速率不断上传 A2」 | 现役把接收解析放进独立线程，界面刷新与之解耦 | 采用 **~8.3ms 一帧** 这个量级做 M3 的容量估算；曲线抽点必须与接收速率解耦（[[踩坑合集]] 里「后台只入队、UI 定时批量消化」那条同样适用） |
| 6 | 包编号范围 | 写作 `0－10000` | 字段是 2 字节；ICC 用 `ushort` | **按 2 字节回绕实现**（0x0000~0xFFFF）；文档的 10000 只是使用建议 |
| 7 | 4 字节 / 浮点字节序 | 「以 KEIL MDK 的 C 编译器联合体（Union）定义的存储顺序为准」，同时又写「2 字节数遵循高字节在前」 | ICC 的 `Gr3CommandWriter` **一律大端**（含 Int32 的联机密钥），联机与读设备 ID 均已跑通 | **一律大端**。文档那句 union 说法与实际不符——目前只被「联机成功」间接证明，**待抓帧确认**（首选 C4 / C6 这类含 Int32 的帧） |
| 8 | CRC-8 覆盖范围 | 「将指令包**帧长度、命令类型、数据**进行 CRC-8 计算」 | 现役 `ValidateCRC8(FRecvBuf, 3, InstrLen)`；ICC 从长度字节起 `instructionLength` 字节 | **一致，无冲突**（「帧长度」所指的那一段） |
| 9 | 数据包长度含义 | 「除去 UDP 包帧头和 数据包长度值本身 之外所有的数据长度之和」 | 现役 `ExpTotal := 3 + 1 + PktLen`；ICC 同 | **一致，无冲突**（长度 = 包编号 + 指令包 + 校验和） |
| 10 | UDP 校验和 | 「除校验和本身之外所有数据的无符号相加保留低 16 位」 | 现役 `CalcUDPChecksum` 取 `Word(Sum and $FFFF)`，大端写入 | **一致，无冲突** |
| 11 | 单数据报多帧 | **文档未写** | ICC 注释明确：「单数据报多帧是与我方下位机开发人员的口头约定，未写入通讯协议文档；实际设备（如 A2 实时流）会批量打包」 | **按多帧实现**（ANX 的 `TryDecodeFrame` 循环消费字节流，天然支持） |

## 已核对通过的部分（M2）

- **CRC-8 表**：ANX 的 `Gr3Crc8.Table` 与现役 `UdpClientEx.pas` 的 `CRCTable` 字面量 **256/256 项一致**（测试 `Gr3Crc8Tests`）。
- **帧布局**：外层与内层结构与文档第一、二章逐字节一致；A1 应答帧与文档 2.2 节的举例 `EE EE EE 0B 00 01 FA FB FC 03 A1 …` **前 11 字节完全对上**（测试 `Gr3FrameCodecTests`）。
- **下行字段**：C0（年月日时分秒 + Int32 密钥）、C2（14 字节 ASCII）、C4（方向 + UInt16 速度）、CA（order=2 读设备 ID）、CB（order=1）与文档第三章一致。

## 仍未闭环的两条

1. **条目 4**：联机后 GR-3 是否自动推 A0 / A4。
2. **条目 7**：含 Int32 的帧是否确实大端。

两条都可以用现役软件自带的**通讯调试窗体**抓帧补齐（现役 `.dpr` 里确实编进了 `uCommunicationDebuggingForm`）。

## 真机抓帧结果（2026-10-10，实体 GR-3 @ 192.168.0.122:5001）

用 ANX 自己的只读探针（`tools\ANX.Tools.Gr3Probe`：只发 C0 联机 / CB 心跳 / CAH 读设备 ID / CAH 读通道配置）**联机成功**。
原始抓帧：`docs\抓帧\gr3-20261010-140424.log`；黄金夹具：`tests\ANX.Protocol.Tests\Gr3\Frames\gr3-live-20261010.hex.txt`；
回归测试：`Gr3LiveFrameTests`（真机帧若与 ANX 的帧长度 / CRC / 校验和 / 命令字任一处不符，解码就会失败）。

上面「仍未闭环的两条」**均已闭环**，另修正一条：

- **条目 4 闭环**：联机后 **A0 会自动推**（70 B 帧 / 数据域 56 B），**A4 不自动推** —— 必须用 CAH(order=2) 主动读。文档「首先返回 A0 和 A4」只对了一半。
- **条目 7 闭环**：C0 的 Int32 密钥**按大端**发出即被设备接受（随后自动回 A0 并以约 190Hz 推 A2，说明合法性验证通过）。文档那句「按 union 存储顺序」与实际不符。
- **条目 11 闭环**：实测每个数据报**打包 5 帧**（425 B = 5 × 85 B），且**包编号逐帧递增**（00 02 → 00 06）。
- **条目 5 修正**：实测约 **190Hz**（约 6 秒内收到 1130 帧 A2 ≈ 5.3ms 一帧），**不是**文档写的 120Hz。M3 的容量估算按 ~190Hz / 每帧 85 B 来。

真机实测的关键数字：

| 项 | 实测值 |
| --- | --- |
| 设备 ID | `1400C2009105032453235302`（24 字符 ASCII） |
| 设备类型 | 2 = **伺服版综合** |
| A0 系统配置帧 | 70 B（数据域 56 B） |
| A1 应答帧 | 15 B（数据域 1 B = 状态） |
| A3 通道配置帧 | 109 B（数据域 95 B） |
| A4 设备信息帧 | 40 B（数据域 26 B） |
| A2 实时数据帧 | 85 B（数据域 71 B）；每个数据报 5 帧 |
| 上行包编号 | 逐帧递增（2 字节大端） |

**结论**：M2 的帧层假设（长度含义、CRC-8、UDP 校验和、命令字、大端、单数据报多帧）**全部被真机验证通过**。
